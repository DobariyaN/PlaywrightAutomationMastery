🎭 What is Playwright?

Playwright is an open-source end-to-end testing framework developed by Microsoft. It lets you write automated tests that control real browsers — Chromium, Firefox, and WebKit — all from a single API using TypeScript, JavaScript, Python, Java, or .NET.

Unlike older tools like Selenium, Playwright was built for the modern web. It handles single-page apps, shadow DOM, network interception, file uploads, and multi-tab scenarios out of the box.

📌 Key Concept

Playwright communicates with browsers using the Chrome DevTools Protocol (CDP) for Chromium, and custom protocols for Firefox and WebKit. This gives it deep, low-level access to browser internals — much faster and more reliable than older WebDriver-based tools.

⚙️ How Playwright Works Internally

Understanding Playwright's internals helps you write smarter, more reliable tests. At its core, Playwright is a Node.js library that speaks directly to browsers over a WebSocket connection using browser-specific protocols.

1

Your test code runs in Node.js

When you run npx playwright test, your TypeScript tests are compiled and executed in a Node.js process.

2

Playwright launches a browser process

Playwright spawns a real Chromium, Firefox, or WebKit browser process on your machine (not a simulator).

3

WebSocket connection is established

Playwright connects to the browser over a WebSocket, sending JSON commands (e.g., "click this element", "navigate to this URL").

4

Browser executes and responds

The browser executes each command and sends back results, events, and errors. Playwright waits for stability automatically.

💡 Tip

This is why Playwright is so fast — there's no HTTP round-trip overhead like old Selenium WebDriver. Commands go directly over a persistent WebSocket connection.

BrowserContext — the key to isolation

A BrowserContext is like an incognito window — it has its own cookies, storage, and session. This is how Playwright keeps tests isolated from each other. Every test automatically gets its own context.

TYPESCRIPT concept-demo.ts 
// Playwright creates these automatically during tests,
// but here's what's happening under the hood:

const browser = await chromium.launch();

// Each context = completely isolated session
const contextA = await browser.newContext(); // User A
const contextB = await browser.newContext(); // User B (no shared cookies!)

// Each page = a browser tab within that context
const pageA = await contextA.newPage();
const pageB = await contextB.newPage();

await pageA.goto('https://example.com');
await pageB.goto('https://example.com'); // independent

⚠️ Common Mistake

Beginners often put all their test logic directly in spec files. This makes tests hard to maintain. Always extract repeated UI interactions into Page Objects and shared setup into Fixtures.

🧩 Page Object Model (POM)

The Page Object Model is a design pattern that wraps every page of your application in a TypeScript class. Instead of writing selectors directly in your tests, you write them once in a page class and reuse them everywhere.

BasePage — shared functionality

TYPESCRIPT pages/BasePage.ts 
import { Page } from '@playwright/test';

// All page objects extend this base class
export class BasePage {
  readonly page: Page;

  constructor(page: Page) {
    this.page = page;
  }

  // Shared utility: navigate to a path
  async goto(path: string = '/') {
    await this.page.goto(path);
  }

  // Wait for network to settle
  async waitForLoad() {
    await this.page.waitForLoadState('networkidle');
  }

  // Take a screenshot (useful for debugging)
  async screenshot(name: string) {
    await this.page.screenshot({ path: `reports/${name}.png` });
  }
}

LoginPage — a real page object

TYPESCRIPT pages/LoginPage.ts 
import { Page, Locator } from '@playwright/test';
import { BasePage } from './BasePage';

export class LoginPage extends BasePage {

  // Define locators once — use everywhere
  readonly emailInput:    Locator;
  readonly passwordInput: Locator;
  readonly loginButton:   Locator;
  readonly errorMsg:      Locator;

  constructor(page: Page) {
    super(page);
    // Best practice: use role/label locators (accessible + resilient)
    this.emailInput    = page.getByLabel('Email');
    this.passwordInput = page.getByLabel('Password');
    this.loginButton   = page.getByRole('button', { name: 'Log in' });
    this.errorMsg      = page.getByRole('alert');
  }

  // Action method: encapsulate the full login flow
  async login(email: string, password: string) {
    await this.goto('/login');
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.loginButton.click();
  }
}

// In your test, it's now clean and readable:
// const loginPage = new LoginPage(page);
// await loginPage.login('user@test.com', 'password');
📌 Key Concept

Notice we use getByLabel and getByRole instead of CSS selectors like .login-btn. These semantic locators are more resilient — they survive UI redesigns and also match how screen readers see the page.

🔌 API Testing with Playwright

Playwright isn't just for UI. Its built-in APIRequestContext lets you make HTTP requests directly — perfect for testing REST APIs or setting up test data without touching the browser.

API Client class

TYPESCRIPT api/ApiClient.ts 
import { APIRequestContext, request } from '@playwright/test';

export class ApiClient {
  private apiContext: APIRequestContext;

  constructor(apiContext: APIRequestContext) {
    this.apiContext = apiContext;
  }

  // POST /auth/login — returns auth token
  async login(email: string, password: string) {
    const response = await this.apiContext.post('/auth/login', {
      data: { email, password }
    });
    return response.json(); // { token: "abc123..." }
  }

  // GET /users/:id — fetch user by ID
  async getUser(id: number, token: string) {
    const response = await this.apiContext.get(`/users/${id}`, {
      headers: { 'Authorization': `Bearer ${token}` }
    });
    return response.json();
  }

  // DELETE /users/:id — clean up test data
  async deleteUser(id: number, token: string) {
    await this.apiContext.delete(`/users/${id}`, {
      headers: { 'Authorization': `Bearer ${token}` }
    });
  }
}

A pure API test

TYPESCRIPT tests/api/user.api.spec.ts 
import { test, expect } from '@playwright/test';

test.describe('User API', () => {

  test('should return 200 for valid login', async ({ request }) => {
    const response = await request.post('/auth/login', {
      data: { email: 'admin@test.com', password: 'secret' }
    });

    // Assert status code
    await expect(response).toBeOK(); // 2xx

    // Assert response body shape
    const body = await response.json();
    expect(body).toHaveProperty('token');
    expect(typeof body.token).toBe('string');
  });

});

🔀 Hybrid Testing (API + UI)

Hybrid tests are the most powerful pattern in a real project. You use the API to set up state fast (e.g., create a user via API), then use the browser to verify the UI reflects that state. This is far faster than doing everything through the UI.

💡 Real-World Pattern

Instead of clicking through a registration form to create a test user before every UI test, just POST to /users via the API. The UI test starts immediately without the slow form flow.

TYPESCRIPT tests/hybrid/user-profile.spec.ts 
import { test, expect } from '../fixtures'; // custom fixtures
import { LoginPage } from '../../pages/LoginPage';

test('user profile shows correct name after API creation', async ({ page, apiClient }) => {

  // ── ARRANGE: create user via API (fast!) ──
  const newUser = await apiClient.createUser({
    name:     'Jane Doe',
    email:    'jane@test.com',
    password: 'securePass123',
  });

  // ── ACT: log in via UI ──
  const loginPage = new LoginPage(page);
  await loginPage.login('jane@test.com', 'securePass123');

  // ── ASSERT: UI shows the correct name ──
  await expect(page.getByText('Jane Doe')).toBeVisible();

  // ── CLEANUP: delete user via API (no UI needed) ──
  await apiClient.deleteUser(newUser.id);
});

🔧 Fixtures & Hooks

Fixtures are Playwright's dependency injection system. They let you define reusable setup/teardown logic that gets injected into tests automatically. Think of them as shared building blocks.

Built-in hooks (beforeEach / afterAll)

TYPESCRIPT tests/ui/login.spec.ts 
import { test, expect } from '@playwright/test';
import { LoginPage } from '../../pages/LoginPage';

test.describe('Login flow', () => {

  // Runs before every test in this describe block
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
  });

  // Runs after ALL tests in this block
  test.afterAll(async () => {
    // clean up shared resources
  });

  test('valid credentials → dashboard', async ({ page }) => {
    const login = new LoginPage(page);
    await login.login('user@test.com', 'pass');
    await expect(page).toHaveURL('/dashboard');
  });

});

Custom fixtures

Custom fixtures let you share things like an authenticated page, API client, or test user across all your tests with zero boilerplate.

TYPESCRIPT fixtures/index.ts 
import { test as base, request } from '@playwright/test';
import { ApiClient } from '../api/ApiClient';

// Extend Playwright's built-in fixtures
export const test = base.extend<{
  apiClient: ApiClient;
  authToken: string;
}>({

  // Fixture: API client available in every test
  apiClient: async ({ }, use) => {
    const ctx = await request.newContext({
      baseURL: process.env.API_BASE_URL,
    });
    await use(new ApiClient(ctx));
    await ctx.dispose(); // auto-cleanup after test
  },

  // Fixture: pre-authenticated token
  authToken: async ({ apiClient }, use) => {
    const { token } = await apiClient.login(
      'admin@test.com', 'secret'
    );
    await use(token);
  },
});

export { expect } from '@playwright/test';
📌 Key Concept

Notice the use(value) pattern. Everything before use() is setup, and everything after is teardown. Playwright automatically calls teardown even if the test fails — no leaking state!

⚙️ Configuration Deep Dive

The playwright.config.ts file is the brain of your framework. Let's walk through it line by line.

TYPESCRIPT playwright.config.ts 
import { defineConfig, devices } from '@playwright/test';
import 'dotenv/config'; // loads .env file

export default defineConfig({

  // Where are the test files?
  testDir: './tests',

  // Run up to 4 tests in parallel (great for CI)
  workers: 4,

  // Retry failed tests once (flakiness protection)
  retries: process.env.CI ? 2 : 0,

  // Fail fast if too many tests fail
  maxFailures: 10,

  // Settings applied to every test
  use: {
    baseURL: process.env.BASE_URL ?? 'http://localhost:3000',
    screenshot: 'only-on-failure', // capture on fail
    video:      'retain-on-failure', // record on fail
    trace:      'on-first-retry',   // trace on retry
    headless: true,
  },

  // Multiple reporters
  reporter: [
    ['html', { outputFolder: 'reports/html' }],
    ['allure-playwright'],
    ['list'], // console output
  ],

  // Which browsers / devices to test on
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome']  } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari']  } },
    { name: 'mobile',   use: { ...devices['iPhone 13']       } },
  ],
});
⚠️ Environment Variables

Never hardcode URLs or credentials in the config. Use a .env file locally and CI/CD environment secrets in production. Add .env to .gitignore immediately!

🌐 Multi-browser Testing

Playwright bundles its own versions of each browser — you don't need to install Chrome separately. Each browser has its own rendering engine, so testing all three catches real cross-browser bugs.

💡 Tip

During local development, run only Chromium to stay fast: npx playwright test --project=chromium. Run all browsers only in CI to save time.

📊 Reporting & Debugging

When a test fails, you need to understand exactly what happened. Playwright gives you several powerful tools for this.

HTML Reporter

Run npx playwright show-report after a test run to open a beautiful interactive HTML report showing pass/fail status, screenshots, and test duration.

Playwright Trace Viewer

Traces record every action, network request, and screenshot in a timeline. When a test fails in CI, download the trace and open it locally:

BASH terminal 
# Open a saved trace file
npx playwright show-trace trace.zip

# Run with trace recording always on
npx playwright test --trace on

Allure Reporter

Allure gives you a rich dashboard with test history, trends, and categorized failures — perfect for sharing with a team or manager.

BASH terminal 
# Install allure
npm install --save-dev allure-playwright

# Generate and open the Allure report
allure generate allure-results --clean -o allure-report
allure open allure-report

Debug Mode

BASH terminal 
# Open Playwright Inspector (step through test interactively)
npx playwright test --debug

# Use UI mode — the most powerful debugging experience
npx playwright test --ui

Automated tests are only valuable if they run automatically on every code change. Here's a GitHub Actions pipeline that runs your full Playwright suite:

YAML .github/workflows/playwright.yml 
name: Playwright Tests

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps

      - name: Run Playwright tests
        run: npx playwright test
        env:
          BASE_URL: ${{ secrets.BASE_URL }}
          API_BASE_URL: ${{ secrets.API_BASE_URL }}
          CI: true

      - name: Upload HTML report
        uses: actions/upload-artifact@v4
        if: always()   # upload even if tests fail!
        with:
          name: playwright-report
          path: reports/html/
          retention-days: 14

✅ Best Practices & Common Mistakes

Best Practices

  • Use semantic locators — prefer getByRole, getByLabel, getByText over CSS/XPath selectors.
  • Keep tests independent — each test must be able to run alone in any order. Never rely on state from a previous test.
  • Use fixtures for setup — don't repeat beforeEach blocks across files; extract to a shared fixture.
  • Use the API for test data — create/clean test data via API calls, not UI flows. Much faster.
  • Avoid hard waits — never use page.waitForTimeout(3000). Use expect(locator).toBeVisible() instead.
  • Group tests with describe — use test.describe to logically group related tests and share beforeEach scope.
  • Name tests clearly — a test name should read like a user story: 'admin can delete a user account'.

Common Mistakes

❌ Mistake 1 — Hard waits

await page.waitForTimeout(3000) is fragile and slow. Replace with await expect(page.getByText('Loaded')).toBeVisible().

❌ Mistake 2 — Brittle selectors

Never use page.locator('.btn-primary-v2-disabled'). Class names change. Use page.getByRole('button', { name: 'Submit' }).

❌ Mistake 3 — Shared state between tests

Never store test results in a module-level variable that multiple tests read/write. Each test must be a clean island.

❌ Mistake 4 — Skipping teardown

Always clean up test data after tests (especially users, orders, records). Stale data causes mysterious failures later.

🎓 Golden Rule

A test that is fast, isolated, readable, and deterministic is worth ten flaky tests. Write fewer, better tests.

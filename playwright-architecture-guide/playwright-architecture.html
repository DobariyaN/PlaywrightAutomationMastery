Playwright End-to-End Architecture

Playwright looks like one library, but it's really a small distributed system: a test script, a translator, a wire, a driver, and three differently-spoken browsers. Once you see how a single click travels through all five, the rest of the API makes a lot more sense.

Architecture diagram

One driver, many languages, three engines

Every Playwright command makes the same trip: out of your script, across a persistent socket, into a single Node.js driver, and out to whichever browser engine is doing the work.

02

Five components, one round trip

Read left to right in the diagram above, or top to bottom here — a command always visits these five stops in order.

A

Client Libraries

Where you write page.click(), in whichever language your team uses.

B

Client / API layer

Converts your API call into a protocol message — the same shape regardless of language.

C

Transport

An open WebSocket carrying JSON-RPC messages, bidirectionally, without polling.

D

Playwright Driver

A single Node.js process. Owns browser lifecycle and actionability checks.

E

Browser Engines

Chromium, Firefox, WebKit — each driven by a different underlying protocol.

03

Tracing page.click("#submit")

Following one command end-to-end is the fastest way to internalize the architecture.

You call await page.click("#submit") in your test file.

The client layer serializes it into a JSON-RPC message describing the action and its target.

The message travels over the persistent WebSocket to the driver; the same socket carries events back the other way.

The driver runs actionability checks — visible, stable, enabled, not obscured — waiting automatically until they pass.

The driver issues a low-level instruction to the correct browser engine, using that engine's own protocol.

The result flows back up the same path and resolves your await in the test script.

04

One driver, three different protocols

Playwright doesn't talk to every browser the same way — this is the detail most guides skip.

EngineReal browsersProtocolWhy
Chromium Chrome, Edge, Chromium-based browsers CDP Chrome DevTools Protocol is built into Chromium already — no patching needed.
Firefox Firefox patched protocol The Playwright team maintains a patched Firefox build exposing hooks not available by default.
WebKit Safari patched, custom protocol WebKit is similarly patched by the Playwright team for reliable automation.
05

executablePath & channel

By default, Playwright launches the patched binaries it downloaded via playwright install. Two driver-level options let you override that choice.

channel

Launch an already-installed real browser build instead — e.g. 'chrome' or 'msedge' — to test against exactly what your users run.

executablePath

Point Playwright at any specific binary on disk, by file path, for full manual control.

06

Why build it this way

Older tools ran a separate driver per browser and injected automation code into the page itself. Centralizing into one out-of-process driver changes the trade-offs:

One source of truth — waiting, retries, and API behavior live in one driver, not reimplemented per language.

A live channel, not polling — the persistent WebSocket streams events (logs, network activity, dialogs) as they happen.

Deliberately patched browsers — controlling the Firefox and WebKit builds gives hooks that stock consumer browsers don't expose.

Glossary

CDP
Chrome DevTools Protocol — Chromium's built-in interface for external control and inspection.
JSON-RPC
A lightweight message format for remote procedure calls; encodes every command and response.
WebSocket
A connection that stays open so both sides can send messages at any time, unlike a normal HTTP request.
Playwright Driver
The Node.js process that receives client commands and controls the browsers.
Actionability checks
Automatic checks — visible, stable, enabled, receives events — run before any interaction.
Browser context
An isolated, incognito-like session inside a browser instance; many can run in parallel.
Headless
Running a browser with no visible window, common in CI pipelines.

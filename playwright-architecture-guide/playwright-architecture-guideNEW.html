01 — introduction

What is Playwright?

Playwright is a browser automation framework built by Microsoft. It lets you write code that controls a real web browser — clicking buttons, filling forms, navigating pages — exactly as a real user would. It's primarily used for end-to-end testing of web applications.

🧪

End-to-End Testing

Test your full application as a user experiences it — browser to server and back.

🌐

Cross-Browser

One API controls Chromium, Firefox, and WebKit (Safari's engine) identically.

⚡

Auto-Waiting

Playwright waits for elements to be ready before acting — no more flaky sleep() calls.

🔗

Multi-Language

Use JavaScript, TypeScript, Python, Java, or C# — all talk to the same engine.

02 — motivation

Why Playwright over Selenium?

Selenium was the standard for 15 years, but it was designed for a different era. Playwright was built from scratch knowing how modern browsers work.

Key insight: The Playwright "server" is always a Node.js process, even when you write tests in Python or Java. Your Python/Java binding talks to the Node.js server over a pipe, which in turn talks to the browser. This is why all language bindings behave identically.
04 — communication protocol

Chrome DevTools Protocol (CDP)

CDP is the language Playwright speaks to Chromium. It's the same protocol your browser's DevTools use — Playwright is essentially automating the DevTools from code. Firefox and WebKit have equivalent internal protocols that Playwright wraps uniformly.

What CDP gives us

  • Navigate to a URL
  • Evaluate JavaScript in a page
  • Intercept and modify network requests
  • Access DOM element geometry
  • Subscribe to page events (load, crash)
  • Capture screenshots and PDFs
  • Control device emulation

CDP message structure

// Command (client → browser) { "id": 42, "method": "Page.navigate", "params": { "url": "https://example.com" } } // Response (browser → client) { "id": 42, "result": { "frameId": "ABCD-1234" } }
Why not WebDriver? WebDriver (Selenium) goes: your code → HTTP request → WebDriver server → browser. That's 2 hops + HTTP overhead. CDP goes: your code → WebSocket → browser. One hop, binary-fast, full-featured access to browser internals.
05 — process model

The Browser Server Process

When you call playwright.chromium.launch(), Playwright spawns a real Chromium process and keeps a persistent pipe to it. This pipe carries CDP messages at high speed. Here's what the request lifecycle looks like when you call page.click():

01

Your test calls locator.click()

The Playwright API creates an internal command object and serializes it to JSON. For a language binding (Python/Java), it's sent over a pipe to the Node.js Playwright Server first.

02

Playwright Server receives the command

The Node.js server translates the high-level command into the appropriate CDP messages. A single click() may involve several CDP calls: DOM.getBoxModel, Input.dispatchMouseEvent.

03

Auto-wait begins

Before clicking, Playwright checks that the element is visible, stable (not animating), enabled, and receives events. It polls every ~100ms until all conditions pass or timeout is reached.

04

CDP messages sent to browser

The server sends Input.dispatchMouseEvent with type mouseMoved, then mousePressed, then mouseReleased — simulating a real physical click, not a synthetic JS click.

05

Browser dispatches the event

The real browser engine fires mouseover, mousedown, click, mouseup events on the element, triggering any attached JavaScript handlers.

06

Result returned to your test

The CDP response flows back through the chain. If a navigation started, Playwright waits for load or domcontentloaded before resolving the promise. Your test continues.

06 — isolation model

Browser Contexts — Playwright's Superpower

This is the feature that makes Playwright fast and reliable. A Browser Context is like a completely isolated browser profile inside one browser process. Each context has its own cookies, localStorage, and cache — completely separate from other contexts.

One Browser Process, Many Isolated Contexts

🌐 Chromium Process
Context A (Test 1)
cookie: session=abc localStorage Page 1 Page 2
Context B (Test 2)
cookie: session=xyz localStorage Page 1
Context C (Test 3)
empty session Page 1
Why this matters for speed: Selenium creates a new browser process per test — slow and memory hungry. Playwright creates one browser process and lightweight contexts inside it. Creating a new context takes ~1ms vs ~2 seconds for a new browser.
example: storageState for authentication reuse // One-time setup: log in and save state const context = await browser.newContext(); await context.page().goto('/login'); await page.fill('#email', 'user@test.com'); await page.click('button[type=submit]'); await context.storageState({ path: 'auth.json' }); // Every test reuses this saved session — no login needed const test = base.extend({ context: async ({ browser }, use) => { const ctx = await browser.newContext({ storageState: 'auth.json' }); await use(ctx); await ctx.close(); } });
07 — page model

Pages and Frames

A Page represents a single browser tab. Inside a page, you can have nested Frames — iframes and sub-frames. Each frame is its own JavaScript execution environment with its own DOM.

Explore the object model

Page is a single browser tab. It wraps a main frame and provides a unified API for navigation, interaction, and events. Key methods: goto(), click(), fill(), screenshot(), evaluate().

One context can have many pages (tabs). Playwright can even handle popup windows — a window.open() creates a new Page you can get with context.waitForPage().

Frames are the building blocks of a page. The main frame IS the page. Each <iframe> element spawns a child frame with its own DOM and JavaScript scope. Playwright handles frames natively — you can query page.frame('name') or page.frameLocator('iframe') and interact with iframe content directly, which Selenium struggles with.

Locator is Playwright's preferred way to find elements. It's lazy — it doesn't find the element until you act on it. This means it automatically re-queries the DOM each time, surviving re-renders and dynamic updates. Locators support chaining, filtering, and role-based queries that mirror how users perceive the page. Example: page.getByRole('button', { name: 'Submit' }).

ElementHandle is the lower-level API — it's a live reference to a specific DOM node at a point in time. If the element is re-rendered, your handle is stale. Playwright recommends using Locators instead. ElementHandles exist mainly for passing elements across evaluate() calls into page JavaScript.

08 — javascript bridge

Execution Context & evaluate()

Every frame has its own JavaScript execution context — it's the same V8/SpiderMonkey/JavaScriptCore runtime that runs your web app's code. Playwright's evaluate() lets you inject and run JavaScript inside this context.

how page.evaluate() works // This function runs INSIDE the browser, not in your test const title = await page.evaluate(() => { return document.title; // ← browser JS }); // Pass arguments into the browser context const result = await page.evaluate(([x, y]) => x + y, [3, 4]); // result === 7 // Expose a Node.js function to page JavaScript await page.exposeFunction('readFile', async (path) => { return fs.readFile(path, 'utf8'); // ← Node.js });
Serialization boundary: Data crossing between your test and the browser must be JSON-serializable. You can't pass functions, class instances, or circular objects. Playwright handles primitives, arrays, and plain objects automatically.
09 — network layer

Network Interception Architecture

Playwright sits between your app and the internet at the CDP level — every network request is visible and interceptable before it leaves the browser.

→

App makes a fetch request

Your web app calls fetch('/api/users'). The browser's network stack prepares the request.

⚡

CDP fires Network.requestWillBeSent

Playwright receives this event and checks it against registered route handlers set up with page.route() or context.route().

✓

Route handler decides what to do

Your handler can: route.fulfill() (return mock data), route.abort() (simulate network error), or route.continue() (let the real request proceed, optionally modified).

network mocking example // Mock an API endpoint with fake data await page.route('**/api/users', route => { route.fulfill({ status: 200, contentType: 'application/json', body: JSON.stringify([{ id: 1, name: 'Alice' }]) }); }); // Modify request headers before they're sent await context.route('**/*', route => { route.continue({ headers: { ...route.request().headers(), 'X-Test-Run': 'true' } }); }); // Simulate slow network await context.setOffline(false); await browser.newContext({ // throttle offline: false, httpCredentials: { username: 'user', password: 'pass' } });
10 — execution model

How Playwright Runs Tests in Parallel

Playwright's test runner uses a worker process model. Each worker is an independent Node.js child process with its own browser. Tests within a worker run sequentially; multiple workers run simultaneously across CPU cores.

Default parallelism = CPU cores. On an 8-core machine, Playwright runs 8 workers simultaneously. You can tune this with workers: 4 in playwright.config.ts. Use test.describe.serial to force a group of tests to run sequentially.
11 — observability

The Tracing Engine

When a test fails, Playwright can replay exactly what happened. The Trace Viewer captures a complete recording of everything — actions, network, console logs, DOM snapshots — as a single .zip file you can open in a browser.

📸

DOM Snapshots

Every action captures the full serialized DOM at that moment. You can replay the page state in the Trace Viewer.

🌐

Network HAR

All HTTP requests, responses, headers, and bodies are recorded in HAR format alongside the timeline.

📹

Video & Screenshots

Playwright can record a video of the test and take screenshots on failure — all captured via CDP.

📋

Console & Errors

Browser console messages and JavaScript errors are captured and timestamped on the trace timeline.

enabling traces in playwright.config.ts use: { // 'off' | 'on' | 'retain-on-failure' | 'on-first-retry' trace: 'retain-on-failure', screenshot: 'only-on-failure', video: 'retain-on-failure', }, // Start/stop traces manually await context.tracing.start({ screenshots: true, snapshots: true }); await context.tracing.stop({ path: 'trace.zip' }); // View: npx playwright show-trace trace.zip
🎓 Summary: What makes Playwright's architecture special
Direct browser protocol — CDP/BiDi, not HTTP middleware chains like WebDriver
Lightweight contexts — isolated sessions without spawning new processes
Universal Node.js server — all language bindings use the same battle-tested core
Auto-wait at every layer — actionability checks built into the API itself
